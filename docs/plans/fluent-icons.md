# Fluent UI icons for status sections and view icons — list-driven names with Fabric fallback

## Context

Issue [#1287](https://github.com/Puzzlepart/prosjektportalen365/issues/1287): status-section icons in `Prosjektstatus` should be Fluent UI v9 icons (Regular by default, Filled on hover), read from the `Statusseksjoner` list, with fallback to the old UI Fabric (MDL2) font icons; the same mechanism should then cover view icons in `Porteføljeoversikt`/aggregated views.

Today the icon *name* already comes from the lists (`GtSecIcon`, `GtPortfolioFabricIcon`, `GtIconName`, `GtPortfolioColumnIconName`) but rendering is split:

- `ProjectWebParts/src/components/ProjectStatus/StatusElement/StatusElementIcon/StatusElementIcon.tsx` renders a Fabric `<Icon iconName style={{ fontSize, color }}>` — the main target. Same for `PortfolioWebParts/src/components/List/ItemColumn/ConfigColumn/index.tsx`.
- The shared `Toolbar` (`shared-library/src/components/Toolbar/createIcon.tsx`) already resolves catalog names to bundled Fluent icons with Fabric fallback, so toolbar-driven view/data-source icons are Fluent *only if the stored name happens to be a catalog key*. Most template defaults are Fabric-only names (`BarChart4`, `DateTime`, `PhotoCollection`, `TimelineDelivery`, …) and render Fabric; only `Money`, `Warning` and `Lightbulb` coincide with catalog keys and already render Fluent.
- `getFluentIconWithFallback(name, bundleWithFilled, color)` in `shared-library/src/icons/index.tsx` has no `size`/`filled`/`className`, and `PortfolioWebParts/src/components/ProjectList/ProjectListFilterRegistry.ts` has its own uncached `bundleIcon` over a deep import of `pp365-shared-library/lib/icons/iconCatalog`.
- No SCSS in the repo toggles `.fui-Icon-filled`/`.fui-Icon-regular`, so bundled icons outside Fluent `Button`/`MenuItem` never fill on hover.

**The bundle-size objection.** The thread proposes `import * as Icons from '@fluentui/react-icons'` so any name resolves; olemp objects that this bloats every bundle. Measured against the installed `@fluentui/react-icons` 2.0.330 (`SharePointFramework/shared-library/node_modules/@fluentui/react-icons`): `lib/icons/chunk-*.js` = 3,577,192 B unminified for 5,778 `createFluentIcon(` modules (≈ 619 B each, mostly SVG path data; 633,630 B gzipped). Every SPFx solution has `externals: {}` and no `splitChunks`, so `pp365-shared-library` is inlined into **each entrypoint** (ProjectWebParts 8, PortfolioWebParts 8, ProgramWebParts 4, ProjectExtensions 4, PortfolioExtensions 5, shared-library 1). A namespace import would therefore add ~3.6 MB unminified / ~634 KB gzip *per bundle*, up to 8× inside one `.sppkg`. The objection is correct. Conversely, the package is `sideEffects: false` with `/*#__PURE__*/`-annotated exports and the shipped bundles prove tree-shaking works today: `project-status-web-part_*.js` contains 203 unique icon modules, not 5,778. A Regular+Filled pair costs ≈ 1.24 KB unminified / ≈ 0.25 KB gzip per bundle copy.

This plan answers the objection by keeping the curated catalog, growing it by exactly the 14 pairs the template defaults need, and moving compatibility for existing tenants into a code-side alias map instead of a wider import.

## Decisions

1. **Curated catalog only — no `import *`, no lazy "all icons" chunk.** Catalog grows from 88 to 102 entries (the 14 pairs in the mapping table). A lazy `import()` extended catalog (precedent: `PackageInstaller.ts`) would force every icon consumer to become async with a placeholder-then-swap flicker on first render (on top of the Fluent v9 surface flashes the portfolio list already had to work around) to save a few KB — not worth it. Two ESLint guards in `SharePointFramework/.eslintrc.yaml` make the rejection mechanical (see shared-library) — deliberate gold-plating beyond the issue; can be split into a follow-up if the review wants a smaller diff.
2. **Legacy Fabric names resolve through a separate `fabricIconAliases` map, never by polluting catalog keys.** DataRows are `UpdateBehavior="Skip"`, so every upgraded tenant keeps `BarChart4`, `DateTime`, `CircleFill`, … forever. Resolving them at render time gives Fluent icons on day one with zero data migration, works under `-SkipTemplate`, and covers customers who typed the same Fabric names themselves. `FluentIconName` stays `keyof typeof iconCatalog` (canonical names only); `getFluentIcons()` (property-pane dropdown) lists canonical names only. Removing an alias later is a breaking change — the file's JSDoc says so.
3. **One resolver, one cache, one public API.** `resolveFluentIcon(name: string): ResolvedFluentIcon | null` (catalog → alias → `null`) becomes the single lookup; `getFluentIconWithFallback`, `isIconAvailable`, Toolbar `createIcon`, `ConfigColumn`, `StatusElementIcon` and the new component-typed `getIconComponentWithFallback` all sit on it and on the existing `bundledIcons` Map. The two deep imports of `pp365-shared-library/lib/icons/iconCatalog` are removed. No `Filled`/`Regular` suffix parsing of list values — the only "filled" need (`CircleFill`) is an alias with `filled: true`. `getIconComponentWithFallback` deliberately changes `ProjectList`'s current behaviour (any unknown name → `Cube`): unknown non-empty names now take the Fabric branch like every other render site, so a Fabric name typed in the property pane renders its glyph and a typo shows the same empty box everywhere instead of silently becoming a cube; only an empty name gets the `Cube` default. This is a deliberate behaviour change beyond the issue, named in the CHANGELOG bullet; if the review wants zero `ProjectList` change, return `getBundledIcon(defaultName)` on a miss instead — one line. The two deep imports of `pp365-shared-library/lib/icons` (not `/iconCatalog`) in `PortfolioWebParts/src/components/List/ColumnContextMenu/renderMenuItem.tsx:12` and `ProjectWebParts/src/components/DynamicList/components/ColumnContextMenu/renderMenuItem.tsx:12` are catalog-only `getFluentIcon` on static registry names — intentionally left alone; the ESLint guard does not match them.
4. **`getFluentIconWithFallback(name, options?)` gains an options object; the positional boolean form is kept as a `@deprecated` overload.** `size`, `filled`, `className` are needed to replace the Fabric `<Icon style={{ fontSize, color }}>` 1:1; `size` maps to `width/height` on Fluent and `fontSize` on Fabric so callers don't care which branch rendered. The four in-repo callers are migrated in the same change; the overload (`typeof options === 'boolean'`) keeps the published package and the `kodemonster.md` example compiling. Empty/undefined names return `null` (never `<Icon iconName={undefined}>`).
5. **`bundle: false` honours `filled`.** `getFluentIcon` returns `filled ? icon.filled : icon.regular` when not bundling (today always `regular`). A static dot (`ConfigColumn`) renders one SVG per cell instead of two, and can never be hollowed by a hover rule.
6. **Hover fill outside Fluent `Button`/`MenuItem` is parent-scoped SCSS with `:global(.fui-Icon-filled)`.** `bundleIcon` renders both SVGs; griffel's own rules are single-class (`.fjseox{display:none}` / `.f1w7gpdv{display:inline}`, specificity 0,1,0). Fluent Button uses exactly this mechanism (`.ft1hn21:hover .fui-Icon-filled{display:inline}`). Our `.element:hover :global(.fui-Icon-filled)` is (0,3,0) and wins regardless of stylesheet order; `:global()` already compiles in this pipeline (`DynamicList/views/ListView/ListView.module.scss`). Every hover rule is paired with `:focus-visible`, and the `.fui-Icon-regular { display: none }` counterpart is mandatory (otherwise both glyphs show). Fluent `Tab` does **not** toggle on hover — verified in the pnpm store (`common/temp/node_modules/.pnpm/@fluentui/react-tabs@9.12.2_*/node_modules/@fluentui/react-tabs/lib/components/Tab/useTabStyles.styles.js`, not hoisted under any solution's `node_modules`): the only `display` toggles are the selected/unselected pairs (`.fxoiby5 .fui-Icon-filled{display:inline}` / `.f16u1re .fui-Icon-filled{display:none}`); the `:hover .fui-Icon-*` rules are `forced-colors` colour rules only. Tabs get filled-when-selected, not filled-on-hover (exercised by Verification 8).
7. **Semantic mapping locked (one table for alias map, template rows and release notes).** `Asterisk → Warning` (Fluent has no Asterisk; matches the risk section; **not** `Sparkle`, which is the product's AI/assistant iconography — `BotSparkle`, `SparkleCircle`, `ArrowCircleUpSparkle`), `SizeLegacy → PeopleTeam` (resource allocation; already in catalog), `Contact → Person` ("Mine prosjekter"; already in catalog), `BarChart4 → DataBarVertical` (closest glyph), `CircleFill → Circle` filled.
8. **`Prosjektkolonnekonfigurasjon` rows and `GtPortfolioColumnIconName` `<Default>` stay `CircleFill`.** The field's SharePoint `CustomFormatter` (`"iconName":"[$GtPortfolioColumnIconName]"`) resolves Fabric MDL2 names only (`CircleFill` exists there; bare `Circle` does not) — changing the 31 rows would blank the coloured dot in the hub list view. The web part renders them Fluent via the alias. This constraint goes into the field description so a future "cleanup" doesn't break it.
9. **Fresh installs get Fluent names; upgraded tenants get aliases; no PowerShell data rewrite in 1.15.0.** `Statusseksjoner`, `Portefoljevisninger`, `Datakilder` rows and the `<Default>` of `GtPortfolioFabricIcon` (→ `Location`) and `GtIconName` (→ `AppsList`, matching the `useEditableView` default so a data source created via list form and via the form panel start with the same icon; a filled dot has no meaning for a menu icon) switch in the templates. `<Default>` changes ride `Portfolio.pnp` on upgrade (Fields handler is not in `$UpgradeExcludeHandlers`). A row rewrite would only change what admins see in list forms, touches customer rows and cannot separate a template default from an identical deliberate value — specified as optional in Install, not shipped.
10. **Editing surfaces: description text carries the contract; no icon picker in this issue.** `GtSecIcon` is editable only in the SharePoint list form, so the four resx descriptions must state: Fluent name from Prosjektportalen's icon set (example), stroke icon that fills on hover, link to the Fluent catalog, UI Fabric names still supported, and (for `GtPortfolioColumnIconName`) the list-view constraint. A `Combobox` icon picker for the two `ViewFormPanel`s is a follow-up (see Out of scope) — it needs a content-oriented catalog to be useful, which is the same bundle debate again.
11. **The Fabric fallback's font registration is a documented transitive coupling.** No first-party code calls `initializeIcons()`/`registerIcons()`; the MDL2 registration is bundled and executed at module load by `@pnp/spfx-controls-react` (`initializeIcons` call verified by grep in `shared-library/node_modules/@pnp/spfx-controls-react/lib/controls/carousel/Carousel.js`, reached through shared-library's root-barrel `import { ModernTaxonomyPicker } from '@pnp/spfx-controls-react'` in `CustomEditPanel/.../TaxonomyFieldType.tsx`) and, in the three web-part solutions only, `@pnp/spfx-property-controls` (`PortfolioWebParts/node_modules/@pnp/spfx-property-controls/lib/common/iconSelector/IconSelector.js`). Whether the SharePoint host page also registers icons is unverifiable from the repo. We do not add a second call now (duplicate registration warns); the edge case records the trigger for adding `initializeIcons(undefined, { disableWarnings: true })` to `shared-library/src/icons/index.tsx` if those imports are ever narrowed.
12. **Keyboard reach for `iconsOnly` icons is optional and scoped to `props.iconsOnly`.** Not requested by the issue. The `.tooltipHost` span is shared with `truncateComment` cards (`useWrapper = !!truncateComment || iconsOnly`), so the `tabIndex`/`role`/`aria-label` attributes are applied only when `props.iconsOnly`, never on full cards. Cost: up to nine new tab stops on the project front page (one per section shown). Drop the attributes (keep the `:focus-visible` CSS) if that tab-order impact is unwanted.

## Implementation

### shared-library

- **`src/icons/iconCatalog.ts`** — add 14 Regular+Filled pairs, named imports, same shape as existing entries: `DataBarVertical`, `CalendarClock`, `Box`, `Trophy`, `BranchFork`, `Globe`, `ImageMultiple`, `RecordStop`, `Timeline`, `TaskListLtr`, `Comment`, `Location`, `Folder`, `TextBulletListTree` (each verified `<Name>Regular`/`<Name>Filled` in `lib/icons/chunk-*.d.ts`). Nothing else; no `lib/sizedIcons`.
- **`src/icons/fabricIconAliases.ts`** (new) — `export const fabricIconAliases: Record<string, FabricIconAlias>` with `type FabricIconAlias = FluentIconName | { name: FluentIconName; filled?: boolean }`. Entries are the "alias" rows of the mapping table (`BarChart4`, `DateTime`, `Product`, `BranchCommit`, `BulletedList`, `PhotoCollection`, `Contact`, `CircleStop`, `LocationCircle`, `TimelineDelivery`, `Asterisk`, `BacklogList`, `SizeLegacy`, `FabricFolder`, `BulletedTreeList`, `ViewList`, `CircleFill: { name: 'Circle', filled: true }`). Not aliased: `ExcelLogoInverse` (brand icon, stays Fabric), `Page`. JSDoc: why the file exists (Skip rows), that entries are permanent, and that the resx descriptions must be kept in sync.
- **`src/icons/types.ts`** — add `ResolvedFluentIcon = { name: FluentIconName; filled?: boolean }`, `FabricIconAlias`, `className?: string` on `GetFluentIconOptions`, and `GetFluentIconWithFallbackOptions = Pick<GetFluentIconOptions, 'bundle' | 'color' | 'size' | 'filled' | 'className'>`.
- **`src/icons/index.tsx`**
  - `export function resolveFluentIcon(name: string): ResolvedFluentIcon | null` — empty → `null`; `iconCatalog[name]` → `{ name }`; `fabricIconAliases[name]` → normalised `{ name, filled }`; else `null`.
  - `getFluentIcon`: `bundle === false` → `filled ? icon.filled : icon.regular`; pass `className` through. `getBundledIcon` remains the only `bundleIcon` call for catalog icons.
  - `getFluentIconWithFallback(name: string, options?: boolean | GetFluentIconWithFallbackOptions, color?: string)`: normalise the boolean form (`@deprecated` JSDoc) to options; `resolved = resolveFluentIcon(name)`; hit → `getFluentIcon(resolved.name, { bundle: options.bundle ?? true, filled: options.filled ?? resolved.filled ?? false, color, size, className })`; miss with non-empty name → `<Icon iconName={name} className style={{ color, fontSize: size }} />` from `@fluentui/react`; empty name → `null`.
  - `export function getIconComponentWithFallback(name: string, defaultName: FluentIconName = 'Cube'): FluentIcon` — resolved → `getBundledIcon(resolved.name)`; unresolved non-empty → cached (second `Map<string, FC>`) Fabric wrapper `(props) => <Icon iconName={name} className={props.className} />`; empty → `getBundledIcon(defaultName)`. Component identity is stable across renders (no `Tab`/`MenuItem` remount).
  - `isIconAvailable(name)` → `!!resolveFluentIcon(name)`.
  - JSDoc on all exports; `src/index.ts` already `export * from './icons'`.
- **`src/components/Toolbar/createIcon.tsx`** — string branch becomes `return getFluentIconWithFallback(item.icon)`; drop the `@fluentui/react` import. Aliases now reach every Toolbar consumer (views, portfolios, data sources) and Fluent `Button`/`MenuItem` supply the hover toggle. An empty string (customer rows with blank `GtIconName`/`GtPortfolioFabricIcon`) now returns `null` — no icon, no empty box — where today it renders `<Icon iconName=''>`; intended.
- **`src/models/PortfolioOverviewView.ts:167`** — `'LocationCircle'` → `'Location'`.
- **`SharePointFramework/.eslintrc.yaml`** (used by every solution's `lint` script) — under `rules:` add `no-restricted-syntax` with selector `ImportDeclaration[source.value='@fluentui/react-icons'] > ImportNamespaceSpecifier` (message: use named imports via the catalog) and `no-restricted-imports` with `paths: [pp365-shared-library/lib/icons/iconCatalog]` (message: use `getFluentIcons`/`resolveFluentIcon`). The two `renderMenuItem.tsx` imports of `pp365-shared-library/lib/icons` (decision 3) are not matched and stay.

## Bundle-size budget

- **Growth**: 14 pairs ≈ 17 KB unminified / ≈ 3.5 KB gzip per bundle copy; per `.sppkg` (zip-compressed) ≈ entrypoints × 3.5 KB → ProjectWebParts/PortfolioWebParts ≤ ~30 KB, others less. Budget: **each `.sppkg` grows ≤ 100 KB** against the Sep 4 baselines (`ls -l SharePointFramework/*/sharepoint/solution/pp-*.sppkg`: project 9,778,568 B; portfolio 14,103,302; program 6,360,210; project-ext 1,751,115; portfolio-ext 1,815,479; shared 2,496,494).
- **Per-bundle icon-module count** — the only zero-tooling check that a namespace import did not leak. `createFluentIcon` is renamed by webpack (`Object(a.e)("NameFilled","1em",…)`), so grep the surviving name string on the ship output (`temp/deploy/*.js` per `config/deploy-azure-storage.json`; mirrored in `release/assets/*.js`). `temp/deploy/` exists only after a ship build (`gulp bundle --ship`; the workspace currently holds only `temp/manifests.*`), so re-measure the baseline on a fresh ship build *before* touching the catalog:

  ```sh
  grep -o '"[A-Za-z0-9]*\(Regular\|Filled\)","1em"' temp/deploy/*.js | sort -u | wc -l
  ```

  Baseline today: **203** in `project-status-web-part` (more than the 176 catalog modules because sub-dependencies also import icons). Expected after the change: **≤ baseline + 28** per bundle that transitively imports `shared-library/src/icons` (28 is the ceiling; common names such as `Folder`, `Comment`, `Box`, `Location` may already be pulled in by a dependency, so a smaller delta is not a failed measurement). A count near **5,778** is the import-all tripwire; the ESLint guard fails earlier at lint time.
- Entrypoint multiplier per solution (all `externals: {}`, no `splitChunks`): ProjectWebParts 8, PortfolioWebParts 8, ProgramWebParts 4, ProjectExtensions 4, PortfolioExtensions 5, shared-library 1.

## Edge cases

- Empty/undefined name (section row without `GtSecIcon`, view without icon): `resolveFluentIcon` → `null`; `getFluentIconWithFallback` → `null` (the `.icon` wrapper span stays so layout is stable); `getIconComponentWithFallback` → `Cube`.
- Fluent name not in the curated catalog (e.g. `Rocket`): falls to the Fabric branch, which renders an empty box — same as a typo today; the descriptions state the catalog limit. Adding it is a 2-line catalog change (kodemonster.md).
- Fabric name with no alias (`Page`, `ExcelLogoInverse`, customer values): renders exactly as today via the Fabric font icon, sized with `fontSize`; no hover effect (single glyph).
- Names coinciding in Fabric and Fluent with different glyphs (`Money`, `Warning`, `Trophy`, `Globe`, `Comment`, `Lightbulb`): existing tenants silently switch glyph style on upgrade — intended; mentioned in release notes.
- `.fui-Icon-regular { display: none }` must always accompany `.fui-Icon-filled { display: inline }`, or both SVGs show. Never place a toggle rule around `ConfigColumn` (dots would hollow); `bundle: false` there makes it moot.
- Specificity: our `(0,3,0)` rules beat griffel's `(0,1,0)`; they only *tie* with a Fluent `Button`/`MenuItem`'s own hover rule, so don't nest section icons inside such controls.
- `iconsOnly` inside `Tooltip`: the hover target is `.tooltipHost`, not `.element`; Tooltip content is portaled, so the nested `<StatusElement />` (30 px, regular) is unaffected.
- Size parity is approximate: Fabric glyphs are `1em` font-size with their own padding; the Fluent 20-unit viewBox has ~2 px internal margin. Accept, or tune `size` in `StatusElementIcon` only if QA objects.
- Fabric fallback registration (decision 11): if `TaxonomyFieldType.tsx` ever imports `@pnp/spfx-controls-react/lib/ModernTaxonomyPicker` or the `@pnp` deps are removed, add `initializeIcons(undefined, { disableWarnings: true })` from `@fluentui/react/lib/Icons` once in `shared-library/src/icons/index.tsx`.
- `isIconAvailable` now true for aliases: `createIcon` must pass the original name to `getFluentIconWithFallback`, not to `getFluentIcon` directly, or alias hits return `null`.
- Deprecated boolean overload: any out-of-repo consumer of the published `pp365-shared-library` keeps compiling; the union type distinguishes the forms.
- `GtIconName` default → `AppsList` also applies to `Hjelpeinnhold` rows created after upgrade; Footer never renders it.
- Prosjektkolonnekonfigurasjon list UI: an admin typing a Fluent name there gets an empty icon in the SharePoint list view but a correct icon in the web part — the field description warns about it.
- Property-pane dropdown (`projectList/index.ts`) lists canonical names only; a tenant that typed an alias name still renders it but sees no selection — acceptable.
- Build order: shared-library → ProjectWebParts → PortfolioWebParts → ProgramWebParts. `rush rebuild -o pp365-shared-library` first so `resolveFluentIcon`/`getIconComponentWithFallback` exist; ProjectWebParts before PortfolioWebParts because the latter bundles `ProjectInformationPanel` (and thus `StatusElementIcon`) from `pp365-projectwebparts/lib` — rebuilding against a stale `lib` ships the old Fabric `<Icon>` in the portfolio panel; ProgramWebParts last (`pp365-portfoliowebparts/lib`).
